# Design for Fidret

Read [AGENTS.md](../../AGENTS.md), the [charter](../../docs/foundation/charter.md) and the canonical [design language](../../docs/design/fidret-design-brief.md). They own authority, company truth, identity and craft. Use the [system map](../../docs/architecture/README.md) to locate canonical sources; generated `website/` is disposable output.

Start with the visitor's question and the page contract. A primary page should establish relevance, identify the actual contribution, provide proportionate evidence and support a useful next step. Inspect the current source and render. Choose the strongest meaningful emphasis before styling details. If the composition could belong unchanged to any technology company, make its artifact or explanation more specific.

For Home, work, people, approach, navigation and contact, use [work presentation and visitor journeys](references/work-and-journeys.md). Curate existing evidence rather than inventing case studies, services, biographies or results. Individual professional experience is not company delivery history. Lab-dependent features and routes must withdraw with the published parent. Keep forwarded deep links understandable independently of Home.

For model-based explanations, use the [interactive craft checks](references/interactive-explanations.md). Start with a useful worked case. A control changes a stated assumption and a visible consequence; keep input, response, reasons and reading order coherent. Preserve exact share/reference state and meaningful fallback. Interaction is not evidence of comprehension.

Retain the licensed fonts, semantic palette and static Astro architecture. Follow [decision 0013](../../docs/decisions/0013-progressive-lab-experiences.md) for bounded enhancement. Use original code-native diagrams and defined values, with actual scope, authors and dates. Shared build/security/publication rules and the [search skill](../fidret-search/SKILL.md) remain applicable. Do not relax runtime policy for decoration.

Compose for reading and action. Use descriptive headings and natural wrapping. Remove repeated mission/development statements before adding styling. A card, rule or number needs an information purpose; a prohibition is not a substitute for judgment. Public copy, metadata, accessible text and downloads contain no em dashes. Keep navigation onsite where required; use only an authorized real contact destination.

Review the whole journey, then its details: wide desktop, tablet, 390/320 px, enlarged text, keyboard, focus, labels, contrast, destinations and relevant empty/error/selected states. A phone that does not overflow may still hide the useful work behind too much introduction. Add assistive-technology and performance checks appropriate to the change and record exact coverage. Do not claim screen-reader listening, field performance or human comprehension from DOM checks.

Run the shared checks and inspect the complete diff. Keep intentional guidance changes and implementation aligned. Record actual evidence, limits and publication state in the task; use [visitor validation](../../docs/design/visitor-validation.md) for the real-reader and inquiry feedback loop. Downloadable files need direct status/type/byte verification; handle any browser save dialog without changing the user's settings.
