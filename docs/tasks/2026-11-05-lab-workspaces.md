## Acceptance criteria

- A useful editable condition is available without a redundant Start action or a long introductory essay.
- Inputs change modeled facts. Every declared combination uses the canonical assessor, with all remaining blockers visible and priority/non-evaluated conditions explicit.
- Two or three controls per situation, a sound starting case, a short open challenge and reset support exploration without requiring a quiz.
- Farm objects name cloud proposal, local controller, equipment/resources and independent care. Factory artifacts fit the selected boundary instead of repeating candidate numbers in unrelated cases.
- One persistent result explains the action and its reasons. Details contain fixed assumptions, accountable people, evidence and references.
- Exact enum-valued conditions survive reload, sharing, Back and reference round trips. Malformed state falls back safely; no storage or remote runtime calls.
- No-JS and initialization failure retain all five useful worked examples. Keyboard, narrow/enlarged layout, focus, reduced motion and selected-state printing remain usable.
- Full shared checks and current-head required CI pass. Record observed behavior separately from inferred usability and actual human research.

## Decisions

Keep the forest/ivory/sage/copper palette and Manrope. The memorable region is the proposal and its decision boundary, with quiet navigation and references. A new generic dashboard or a larger quiz would retain the original flaw. The chosen composition places conditions beside a meaningful artifact and its result. Mobile brings the response immediately after the inputs.

The complete finite input space is evaluated at build time using the existing policy models. Escaped inert data attributes carry the lookup; the approved browser module only selects and renders a result. This avoids duplicated browser policy, invented physical quantities and new runtime dependencies. Each situation fixes the unexposed assumptions explicitly.
